# Step 12 native platform integration

Implementation date: 2026-09-10

This document is the Step 12 handoff for the existing Capacitor iOS and Android apps. The core web UI was not redesigned. See [the pre-implementation audit](./step-12-native-platform-audit.md) for the original state and prioritized findings.

## 1. Native features added

- A privacy-minimal, versioned prayer snapshot generated by the existing TypeScript prayer logic and cached for native widgets (full current day + upcoming days).
- iOS Next Prayer widget family, iOS Daily Prayers medium widget, and equivalent Android next-prayer/daily-prayer widgets.
- Explicit first-launch and stale-data recovery states.
- Prayer-boundary refreshes without a one-second native refresh loop.
- End-to-end widget, launcher shortcut, local-notification, and push-notification routing into allowlisted app destinations.
- Theme-aware native status-bar behavior and Android navigation-bar colors.
- Four Android launcher shortcuts: Prayer Times, Quran, Qibla, and Zikr.
- A monochrome Android notification icon, corrected adaptive-icon resource selection, and a shorter native splash handoff.
- iOS privacy manifests for app-local and App Group `UserDefaults` access.
- Removal of the legacy charity widgets and cached donation totals from native shared storage.

The existing Quran and saved-hadith share actions already use `navigator.share` when the OS WebView provides it, with clipboard behavior kept separate or used as a fallback. No additional share dependency was necessary.

## 2. iOS implementation

`DeenCompanionWidgetsExtension` exposes two prayer widgets:

- `PrayerWidget`
  - `systemSmall`: next prayer, time, relative time, and date when current.
  - `systemMedium`: next prayer plus the next two upcoming entries and date.
  - `accessoryRectangular`, `accessoryCircular`, and `accessoryInline`: compact Lock Screen presentations.
- `AllPrayersWidget` (`systemMedium`): full Fajr→Isha schedule for today (or tomorrow after Isha), with the next prayer highlighted.

WidgetKit reads one JSON snapshot from the existing App Group (`group.com.deencompanion.app`). Timeline entries are scheduled at cached prayer boundaries, and the app reloads widget timelines after shared data changes and when it becomes active. The widget extension target is iOS 17 rather than the accidental iOS 26 setting, matching the SwiftUI APIs used by the extension.

The separate Swift prayer calculator was removed to eliminate drift and maintenance duplication. The overlapping legacy `PrayerListWidget` remains removed; Daily Prayers covers the full-day use case. Non-prayer widgets remain except Charity, which was removed because donation totals are private. All remaining widget URLs now use the registered `com.deencompanion.app` scheme. App and extension privacy manifests declare the required App Group/defaults reasons.

## 3. Android implementation

The compact `PrayerTimesWidget` and medium `AllPrayersWidget` read the same normalized snapshot from Capacitor Preferences. Both schedule an inexact `AlarmManager.setAndAllowWhileIdle` boundary alarm (plus a 30-minute AppWidget fallback), so the previously declared exact-alarm permission is no longer needed. `AllPrayersWidget` prefers today's full five times when present, otherwise tomorrow after Isha (`TOMORROW` header). Both widgets present Android-native opaque light/dark surfaces, system typography, no emoji decoration, and clear setup/stale copy.

A small Capacitor bridge broadcasts widget updates immediately after a new snapshot is written. Widget taps and all four static launcher shortcuts use `ACTION_VIEW` URIs under `com.deencompanion.lite`. The unused route extras and separate Kotlin prayer calculator were removed.

Modern adaptive icons now resolve to the existing branded crescent foreground instead of the template Android robot. The splash handoff is reduced from two seconds to 500 ms with a short fade, and obsolete template splash PNGs no longer override the branded launch surface. System navigation/status colors and a dedicated monochrome notification crescent were added.

## 4. Shared widget data architecture

Key: `widget_prayer_snapshot_v1`

The app writes one bounded JSON object:

| Field | Purpose |
| --- | --- |
| `version` | Contract migration guard; currently `1`. |
| `generatedAt`, `expiresAt` | Freshness and safe stale-state boundaries. |
| `locationLabel` | Optional city-level label only. |
| `timezone` | IANA timezone used by the app calculation. |
| `gregorianDate`, `hijriDate` | Compact display context. |
| `prayers[]` | Allowlisted prayer name, display time, absolute timestamp, and local day key. Includes the **full current local day** (past + future) so Daily Prayers can render all five times, plus remaining future days for next-prayer timelines. |
| `nextPrayer` | First future occurrence (`timestamp > generatedAt`) from the same normalized list. |
| `deepLink` | Fixed `/times` destination. |

The TypeScript app remains the sole prayer-calculation source. Native readers validate version, size, timestamps, prayer names, date keys, and expiry before display. The snapshot contains no latitude/longitude, account identifiers, credentials, or donation information. Old coordinate/config and charity-total keys are removed from Preferences and App Group storage on native launch and subsequent prayer writes.

The native shells also include a temporary compatibility normalizer for the deployed web bundle, which still writes the earlier app-computed 14-day schedule keys. It converts those cached results into the same v1 snapshot (full current day onward, not future-only) without performing prayer calculation natively. If an existing future-only v1 cache cannot fill today's five times, migration remaps from the legacy schedule once. This keeps store/simulator builds functional before the updated web bundle is deployed and can be removed after the deployment migration window.

## 5. Refresh behavior

- App launch/location/method/madhab changes regenerate the multi-day snapshot.
- Native foreground events trigger the existing prayer fetch and then rewrite the snapshot.
- iOS schedules WidgetKit timeline transitions at each cached prayer boundary.
- Android schedules one inexact alarm for the next boundary and retains the platform's 30-minute periodic fallback.
- Android widgets are also broadcast-refreshed immediately after a cache write.
- Neither native implementation runs a second-by-second background process. iOS may render system-managed relative text; Android renders a concise stable time-until value until its next boundary/fallback refresh.

## 6. Deep links

Widget and shortcut routes use each platform's existing custom URL scheme and are converted to internal routes by a strict allowlist. Supported destinations include Prayer Times, Quran, Hadith, Zikr, Calendar, Charity, and Mosques; the former `/qibla` widget path maps to Prayer Times, where Qibla currently lives. URLs with unknown schemes, hosts, or app routes are rejected.

Local notification `extra.url` and push notification `data.url` now use the same router. Existing OAuth callback handling remains separate and unchanged.

## 7. Setup and signing

- Keep App Groups enabled for both the iOS app and `DeenCompanionWidgetsExtension`, using `group.com.deencompanion.app`.
- Keep the current iOS application identifier and Android application ID; the platform-specific schemes intentionally differ.
- Open `ios/App/App.xcworkspace`, not the `.xcodeproj`, because Capacitor plugins are installed through CocoaPods.
- Release archives still require the project's existing Apple signing team/profiles and Android release keystore. No new entitlement, secret, native dependency, API key, or background mode was added.
- Android compilation requires Java 21; Android Studio's bundled runtime is suitable.

## 8. Platform limitations

- WidgetKit controls actual reload timing and applies a daily refresh budget. Timeline entries make predictable prayer transitions reliable, but the OS may defer reload requests.
- Android ignores `updatePeriodMillis` values below 30 minutes and may defer inexact alarms in low-power modes. The widget therefore favors correctness at known boundaries plus app-driven refreshes over continuous countdown animation.
- Android launchers vary in widget dimensions, masking, and Lock Screen widget support. Information parity is provided on the home screen; no launcher-specific Lock Screen promise is made.
- iOS Home Screen quick actions were not added because the existing app has no native cold-launch quick-action routing layer; Android static shortcuts were low-risk within its URI intent architecture.
- Native widget screenshots require a booted/signed simulator or device with the app launched once so a real snapshot exists. Placeholder and recovery states remain available in Xcode previews.
